# «ФінКит» — автоматизоване тестування, спринт 4

**Команда:** Finkitiky  
**Продукт:** «ФінКит» / демонстраційний банківський застосунок ParaBank  
**Репозиторій:** https://github.com/Anton367/tsqa  
**Модуль, який тестуємо в спринті 4:** **«ФінКит» v1.0.0**  
**Технології:** JDK 17, Maven, JUnit 5, Selenium WebDriver 4, Selenium IDE, GitHub Issues і Pull Requests.

## 1. Мета спринту

Автоматизувати перевірку бізнес-логіки модуля «ФінКит» версії **v1** за вимогами `BL-10`–`BL-80` і ключових сценаріїв інтерфейсу, описаних у тест-кейсах спринту 3. Зберегти відтворювані тести, результати запуску, звіти про дефекти й докази рецензування в командному репозиторії.

> **Важливо про версії:** у спринті 4 перевіряємо **v1**, у якій навмисно залишено дефекти. Наданий окремо модуль **v2.0.0** призначений для подальшої регресійної перевірки. Не підміняйте код v1 кодом v2 під час підготовки результатів спринту 4. Якщо в отриманому `pom.xml` зазначено `<version>2.0.0</version>`, це **не доказ**, що в `src/main/java` лежить v1; перевірте самі Java-класи та узгодьте версію Maven-проєкту з фактичним вмістом.

## 4. Вимоги до робочого середовища

- **JDK 17** (наприклад, Eclipse Temurin).
- **Apache Maven 3.9** (або сумісна встановлена версія).
- **Google Chrome** для WebDriver-сценаріїв; Selenium Manager із Selenium 4 керує драйвером.
- **Selenium IDE** (розширення браузера) для запису 1–2 сценаріїв.
- Доступ до Інтернету для UI-тестів на `https://parabank.parasoft.com/parabank/index.htm`.

Перевірка середовища:

```bash
java -version
mvn -version
```

Обидві команди повинні показати, що Maven використовує **Java 17**. На macOS за потреби можна встановити `JAVA_HOME`:

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
```

Для Windows/Linux шлях до JDK 17 налаштовується відповідно до системи.

## 5. Підготовка проєкту

1. Клонуйте репозиторій і відкрийте його корінь у терміналі або IntelliJ IDEA:

   ```bash
   git clone https://github.com/Anton367/tsqa.git
   cd tsqa
   ```

2. У `src/main/java/ua/kpi/tzyapz/finkit/` перевірте наявність п'яти класів **версії v1**: `LoanCalculator.java`, `TransferValidator.java`, `AccountLedger.java`, `TransferError.java`, `LedgerEntry.java`.
3. Переконайтеся, що `pom.xml` містить JDK 17, JUnit 5.10.2, Selenium 4.21.0 та Maven Surefire, а `src/test/java/ua/kpi/tzyapz/finkit/` використовується для тестів.
4. Переконайтеся, що тести інтерфейсу мають анотацію `@Tag("ui")`.
5. Перевірте, що у `.gitignore` виключено `target/`, `.idea/` та тимчасові файли IDE.

**Контроль перед запуском:** назва і версія модуля в наданому README v2 або в початковому `pom.xml` не замінюють перевірку того, який вихідний Java-код фактично підключено.

## 7. Що перевіряється

### 7.1. Бізнес-логіка: JUnit 5

| Клас модуля | Вимоги | Тестовий клас | Автори |
|---|---|---|---|
| `LoanCalculator` | `BL-10`, `BL-20`, `BL-30` | `LoanCalculatorTest.java` | Ліза — 5 методів |
| `TransferValidator` | `BL-40`, `BL-50`, а також відкриті питання щодо `BL-60` | `TransferValidatorTest.java` | Антон — 5, Маша — 5 методів |
| `AccountLedger` | `BL-70`, `BL-80` | `AccountLedgerTest.java` | Даша — 5 методів |

Очікувані результати беруться зі специфікації SRS 1.1 та узгоджених рішень щодо вимог, **не з поточної поведінки помилкового v1**. Кожен тестовий метод повинен мати `@DisplayName` з ID вимоги. Для граничних значень використовуються параметризовані тести, для винятків — `assertThrows`, для пов'язаних перевірок — `assertAll` за потреби.

Один параметризований **метод** рахується як один тестовий метод у нормативі авторства незалежно від кількості наборів даних.

Детальні кроки, локатори й очікування фіксуються в `docs/sprint4/ui-scenarios.md`. Наявність кейсу в плані ще не означає, що тест реалізований або пройшов.

## 8. Запуск тестів

Команди виконуються **з кореневої папки Maven-проєкту**, де лежить `pom.xml`.

### 8.1. Юніт-тести (без UI)

UI-тести з тегом `ui` у наданій конфігурації Surefire за замовчуванням виключені:

```bash
mvn clean test
```

### 8.2. Окремі JUnit-класи

```bash
mvn test -Dtest=LoanCalculatorTest
mvn test -Dtest=TransferValidatorTest
mvn test -Dtest=AccountLedgerTest
```

### 8.3. Юніт- та WebDriver-тести разом

```bash
mvn test -DexcludedGroups=none
```

### 8.4. Один UI-тест

```bash
mvn test -Dtest=SecurityUiTest -DexcludedGroups=none
```

Для UI-тестів потрібні встановлений Chrome, доступність ParaBank і сумісна конфігурація Selenium. Для демонстрації одного тесту з **видимим браузером** запускайте локальну конфігурацію без headless-режиму; звичайний автоматизований запуск може бути headless.

**Увага:** `mvn clean test` на v1 може завершитися `BUILD FAILURE` через **коректно виявлені дефекти продукту**. Це не потрібно приховувати: кожне очікуване падіння має бути пов'язане з перевіреною вимогою і GitHub Issue. Решта тестів повинні проходити. Не змінюйте очікувані значення та не вимикайте тести лише заради `BUILD SUCCESS`.

## 9. Результати запуску (Surefire)

Maven Surefire створює результати в:

```text
target/surefire-reports/
```

Даша готує короткий відтворюваний протокол у `docs/sprint4/surefire-summary.md`: дата, коміт або версія коду, команда запуску, кількість тестів, `Failures`, `Errors`, `Skipped`, перелік червоних тестів і відповідні Issue ID. Числові підсумки записуються **тільки за фактичним виводом Maven**.

`target/` зазвичай не додається до Git. Підсумковий текстовий протокол — частина документації спринту.

## 10. Дефекти модуля v1

**Трекер:** https://github.com/Anton367/tsqa/issues  
**Обов'язкова мітка:** `module`.

Для кожного підтвердженого дефекту потрібні:

1. Назва, вимога `BL-ID`, вхідні дані та кроки відтворення.
2. Очікуваний результат згідно з вимогою та фактичний результат на v1.
3. Назва тест-класу й тестового методу, що відтворює проблему, і доказ із Surefire.
4. Severity, Priority, статус і посилання на Issue.
5. Незалежне рецензування баг-репорту.

**Розподіл обов'язків:** автор тесту створює Issue; Маша перевіряє якість звіту; Ліза як КТ підтверджує дефект і погоджує пріоритет. Мінімум для команди з чотирьох осіб — **4 підтверджені дефекти v1**.

Знайдене падіння — **кандидат** на дефект, поки не перевірено очікування за SRS і не підтверджено результат. Наприклад, хронологічний порядок `AccountLedger.history()` прямо описаний у Javadoc модуля, але його зв'язок із `BL-80` у SRS потребує уточнення в матриці покриття.

## 11. Відкриті питання до бізнес-вимог

Питання та рішення докладно фіксуються в `docs/sprint4/README.md` у розділі **«Уточнення вимог бізнес-логіки»**.

- **BL-40 — денний ліміт.** У SRS 1.1 є позначка `[ПІДТВ.]` для 100 000 грн, натомість у коді v1 використано 50 000 грн. Потрібне підтвердження правильного правила; спірне значення не можна автоматично зараховувати як дефект.
- **BL-50 / BL-60 — IBAN.** `TransferValidator.isValidIban()` у v1 перевіряє формат `UA` + 27 цифр, тоді як у SRS передбачено перевірку контрольних цифр MOD-97. Слід окремо перевірити відповідність BL-60 та зафіксувати рішення.
